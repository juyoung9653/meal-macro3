## 행복도시락 일일식수 출력 (2026-11-02)

- main의 중식/일일배송 양식과 기사·지역별 렌더링을 이식한다. 적격·상태·학교 일정·대체식·배송 형태는 SQLite의 실제 배송 판정을 사용하며 예전 자유 입력 비고 파서는 이식하지 않는다.
- 조식·석식은 한 시트, 중식은 별도 시트로 같은 파일에 생성한다. 날짜 역순이며 중식 시트에 중식_ 접두사를 붙인다. 조식 주말 묶음 등 실제 전달하는 끼니 수를 합산한다. 가구별 식수 분포는 DB 가구 소속 기준이며 주소 문자열로 가구를 재분류하지 않는다.
- 기사·지역 매핑 결과 중 빈 값이 있으면 미분류로 모은다. 중식 기사 순서와 조식/석식 기사 순서를 적용하며 합친 시트에 석식이 있으면 석식 순서를 우선한다. 기사별 병합·합계·구분선은 자동 생성하고 원본 양식 서식을 복제한다.
- daily_report 매핑은 급식·행복도시락별로 따로 저장하며 각 양식 안에서 식종 공용이다. 두 양식 모두 현재 운영 DB의 1순위·2순위 설정을 적용한다. 두 양식의 비고 기본값은 `식종 변경 이력`이며 개인 비고 등 다른 칼럼과 1순위·2순위로 연결할 수 있다. 명시적인 비움은 이력 출력도 끈다. 선택한 과거 원본으로 배송량을 계산하며 양식 두 종류의 사용 바이트를 임시로 고정하고 각각 이름·크기·해시를 생성 기록에 남긴다. 출력은 기존처럼 무암호이며 게시·이력 저장 실패 처리를 공통 경로로 유지한다.

- 행복도시락은 main처럼 기사별 식수 소계와 맨 아래 전체 식수 합계를 유지한다. 보조 열 G·J는 원본 양식대로 숨기고 인쇄 범위는 I열까지 유지한다. 포장 분포 계산은 기존 보조 열에 보존하며 새로운 표시 열을 추가하지 않는다. 묶인 열의 min/max와 너비도 복제한다.
- 조식·석식·중식은 선택일이 속한 월요일~일요일 안에서 해당 식종의 양수 식수가 있는 배송일을 참조한다. 선택일에 식수가 있으면 당일, 없으면 같은 주의 가장 최근 앞선 배송일, 앞선 배송도 없으면 같은 주의 첫 이후 배송일을 사용한다. 예: 2026/11/3 조식은 기본 배송 설정에서 11/6을 참조하고 금요일 석식은 같은 주 목요일을 참조한다. 선택한 배송 형태 필터를 먼저 적용하며 이전 주·다음 주의 식수는 가져오지 않는다. 그 주에 식수가 없거나 해당 행·식종에 식수가 없으면 빈칸이며 0을 출력하는 소계·합계 수식도 만들지 않는다. 중식도 대상 식종을 선택했고 가입 기록이 있으면 빈 양식을 유지한다. 참조일 조회 범위를 그 주 일요일까지 넓히되, 선택 기간 밖의 중식 학교 일정 누락은 식수 0으로 취급하고 선택 기간의 기존 일정 검증은 유지한다.
- 참조일의 식수·기사·지역·비고·가구 분포를 함께 표시하고 생성 기록의 `display_reference_days`에 세 식종의 참조일을 남긴다. 반환하는 shipments 및 실제 배송·청구 계산에는 선택 기간의 실제 배송만 포함한다. 기본 양식 파일은 `assets/급식`·`assets/행복도시락`에 직접 둔다.

# 상태, entitlement, 물리 배송 규칙

새 SQLite 앱은 상태 사건, 서비스일별 식수, 실제 배송 이벤트를 서로 다른
개념으로 유지한다. 이 구분은 날짜별 배송 화면, 일일식수, 배송대타와 청구서가
같은 계산 결과를 사용하기 위한 계약이다.

## 상태 사건과 유효 기간

`StatusEvent`는 사용자가 입력한 상태, 기간, 기록 시각과 원문을 그대로 보존한다.
`resolve_status_history`는 다음 규칙으로 `StatusInterval`을 계산한다.

- 나중에 기록한 사건은 자신이 덮는 날짜에서만 이전 사건보다 우선한다.
- 기록 시각이 같으면 ledger에서 뒤에 온 사건이 우선한다.
- 계산된 같은 상태가 붙어 있으면 원본 사건 ID를 합쳐 한 기간으로 만든다.
- 열린 `17일 중지`가 열린 `19일 배송`으로 영구 대체되면 17~18일의 계산 상태는
  `일시중지`다. 두 raw 사건은 모두 남는다.
- 유한한 배송 예외 뒤에 기존 중지가 다시 적용되면 중지를 일시중지로 바꾸지 않는다.
- 명시적인 상태 기간 밖에서 가입된 식종의 기본 상태는 배송이다.

## Entitlement

`decide_entitlement`는 사람·식종·서비스일마다 다음 세 입력을 독립적으로 본다.

1. 그 날짜의 식종 가입 여부
2. 학교 일정 등을 반영한 업체 서비스 제공 여부
3. 계산된 배송·일시중지·중지 상태

세 조건을 모두 만족할 때만 `MealEntitlement`가 생긴다. 제외될 때는 미가입,
서비스 없음, 일시중지, 중지 사유를 함께 남긴다. 따라서 청구 수량은 물리 배송
행이 아니라 entitlement 개수다.

중식 일정의 `O`는 학교가 급식을 제공해 업체 서비스가 없다는 뜻이고, `X`는 학교
급식이 없어 업체 서비스가 있다는 뜻이다. `O`인 날도 `6학년 미급식`처럼 typed된
학년 override가 있으면 해당 학년은 업체 서비스 대상이다. 주말에는 중식 서비스가
없다.

## 학교 일정 Excel 가져오기

명단 상단의 `학교 일정`은 학교별 방학식·개학일 자료를 명단 Excel과 별도로 가져온다.
기본 구조는 헤더 2행, 데이터 3행이며 다음 열 이름을 자동으로 찾는다.

```text
학교명 · 시작일 · 시작일 O/X · 종료일 · 종료일 O/X · 비고(선택)
```

- 날짜는 Excel 날짜 셀, `2026.08.19`, `8월 19일`처럼 연도가 생략된 값을 읽는다.
- 학교명이 실제 병합 셀로 이어진 행만 병합 범위의 학교명을 사용한다. 일반 빈칸을
  임의로 앞 학교와 합치지 않는다.
- 자동으로 찾은 열이 맞지 않으면 파일 화면에서 시트, 연도, 헤더·데이터 행과 각 열을
  다시 선택할 수 있다.
- 다음 검토 화면의 학교별 표에서 학교명, 시작일·종료일과 양쪽 O/X를 직접 수정한다.
- 전체 검토 기간은 사용자가 바꿀 수 있고, 해당 기간의 모든 중식 평일에 근거가 생겨야
  저장할 수 있다.
- 자연어 비고는 자동 확정하지 않는다. `반영 안 함`, `업체 배송(X)`, `학교 급식(O)` 중
  하나를 고르고 필요한 기간·학년을 확인해야 저장 버튼이 열린다.
- 저장하면 학교 전체의 검토된 일정이 하나의 revision으로 남고 즉시 검증 자동 백업을
  만든다. 다음 차수 파일은 기존 학교 일정과 합쳐 새 revision으로 저장한다.

## 저장된 학교 일정 직접 수정

명단 상단의 `학교 일정`은 저장 일정이 있으면 Excel 선택창보다 DB 편집 화면을 먼저
연다. 저장 일정이 하나도 없거나 사용자가 `Excel에서 새로 가져오기`를 누르면 위의
Excel 가져오기 절차로 이어진다.

- DB에는 원본 Excel 행이 아니라 학교별 모든 검토 평일의 canonical O/X와 학년 예외가
  저장된다. 편집 화면의 행은 이 값을 같은 rule이 이어지는 기간으로 묶어 보여주는
  손실 없는 표시이며, 원본 Excel 행을 추정해 복원한 값이 아니다.
- 학교를 고른 뒤 기존 구간의 시작일·종료일·O/X·학교 급식 없는 학년을 수정한다.
  구간을 줄이면 빠진 앞뒤 평일은 이웃 구간의 rule로 자동 연결하고, 구간을 늘리면
  늘어난 평일에 선택한 rule을 적용한다.
- `선택 범위에 새 기간 지정`은 기존 구간 경계를 움직이지 않고 입력한 평일만 새
  rule로 덮어쓴다. 날짜는 한 개의 저장 검토 범위 안이어야 하며 주말만 있는 기간은
  저장할 수 없다.
- `O`는 학교 급식으로 센터 중식 배송이 없고 `X`는 학교 미급식으로 센터 중식 배송이
  있다. O 구간에 학년을 적으면 해당 학년만 센터 배송 대상이 된다.
- 여러 학교의 수정을 화면 안에 모을 수 있고 `이 학교 원래대로`로 학교별 임시 수정을
  취소한다. 표 반영만으로 DB는 바뀌지 않으며 `변경 일정 저장`을 눌러야 확정된다.
- 실제로 달라진 학교만 각각 한 `school-lunch.schedule` update가 되고, 사용자 작업
  전체는 import batch가 없는 UI revision 하나로 저장된다. 최초·마지막 변경 평일,
  변경 평일 수와 O/X 전후 구간을 decision manifest에 남기고 즉시 자동 백업한다.
- 아무 값도 달라지지 않으면 revision을 만들지 않는다. Excel 재가져오기로 이동할 때
  임시 수정이 있으면 버릴지 먼저 확인한다.

청구서·확인서의 반복 서비스 계산은 조식을 가입된 금·토·일,
중식을 검토된 학교 일정이 `X`로 허용한 평일, 석식을 월~목 주 4회 서비스로 계산한다. 사람의
가입 기간 밖 날짜에는 학교 일정이 필요하지 않지만, 가입된 중식 날짜를 덮는 검토 일정이
없으면 조용히 추정하지 않고 문서 생성을 막는다. 휴무의 `미제공`은 제외하고 `대체식`은
원래 서비스일 청구를 유지하며, 날짜별 상태와 서비스일 유효 단가도 같은 계산에 적용한다.

개인·식종별로 제공 요일을 지정하면 조식과 석식은 지정된 요일만 정기 서비스일로
계산한다. 중식은 지정 요일이더라도 검토된 학교 일정이 업체 서비스를 허용해야 한다.
지정 요일 밖의 중식 날짜에는 학교 일정을 조회하지 않는다. 별도 요일이 없으면 위 기본
일정을 유지한다. 휴무의 미제공·대체식 처리는 지정 요일로 결정된 원래 서비스일에
기존 규칙대로 적용한다. 배송 형태는 자유롭게 적을 수 있으며 식수와 단가를 바꾸지 않는다.

## 조식 묶음배송

기본 물리 배송 calendar는 평일 영업이며 휴무일과 예외 영업일을 날짜별로 덮어쓸
수 있다. 정상 금요일에는 금·토·일 entitlement를 금요일 한 배송으로 묶는다.
배송은 한 건이어도 식수는 세 건으로 유지한다.

선택 정보의 `배송 설정`에서 선택한 사람의 설정을 변경한다. `같은 가구 전체에 적용`을
선택하면 조회일 기준 같은 가구원에게 함께 저장한다. 적용 대상을 표시하고, 제공 요일 체크 아래의 `배송요일`에서 각 식사일의 실제 배송 요일을
지정한다. 별도 지정 체크 없이 값을 수정하면 기본값과 다른 항목만 별도 설정으로
판정하며, 식종별 초기화와 전체 초기화로 기본값을 복원한다. 지정한 요일은 해당 식사일 당일 또는 그 이전의 가장 가까운
요일이며, 월요일분을 금요일로 정하면 전주 금요일에 배송한다. 월·연도가 달라져도
같은 규칙을 적용한다. 별도 지정이 없으면 조식 금·토·일분은 금요일 배송이며,
다른 식종은 제공 당일 배송을 따른다. 배송요일만 바꾸어도 별도 설정으로 저장한다.

묶음배송은 청구 식수를 합치거나 줄이지 않는다. 청구·확인서는 원래 제공일의
가입·상태·단가를 적용하고, 일일식수는 실제 배송일에 해당 식사일들을 합산한다.
날짜별 `미제공`과 명시적인 `대체식 제공` 지정은 기존 흐름을 유지하며, 대체식의
실제 제공일은 반복 배송요일보다 우선한다.

과거 `delivery.breakfast-policy` 변경 이력은 보존한다. 별도 `조식 배송 규칙` 설정
화면은 제공하지 않으며, 과거 선택을 새 일일식수의 규칙으로 적용하지 않는다.

## Import reconciliation

import mapping profile은 표준 profile 열, `식종` 열 하나 또는 조식·중식·석식 개별
여부 열, 배송담당·순서와 custom field 열을 version과 함께 정의한다. 제공기관은 Excel
열에 연결하지 않고 GUI에서 직접 입력하며, `provider_value`로 profile version에 저장해
해당 import의 모든 사람에게 동일하게 적용한다. typed observation에는 원본 전체 경로가
아니라 basename, 시트명과 행 번호만 남긴다.

통합 식종 셀은 전체 값의 정확한 일치가 아니라 식종명 부분일치로 읽는다. 예를 들어
`연중 조식`, `석식 대상`, `중식(방중)`에서 각각 조식·석식·중식을 찾고, 한 셀에 여러
식종명이 들어 있으면 모두 선택한다. 지원하는 식종명이 하나도 없을 때만 오류로 막는다.

생년월일 열은 Excel 날짜 셀과 `YYYYMMDD`뿐 아니라 6자리 `YYMMDD`와
주민등록번호·외국인등록번호도 읽는다. 6자리는 현재 연도보다 늦지 않는 가장 가까운
세기로 해석한다. 예를 들어 2026년 기준 `150302`는 2015-03-02,
`990405`는 1999-04-05다. Excel 숫자 셀이 맨 앞 `0`을 없앤 5자리 값도 복원한다.
`150302-3******`, `1503023123456`처럼 뒷자리 첫 숫자가 보이면 그 숫자로
출생 세기를 정하고 앞 6자리만 생년월일로 변환한다. Excel이 2000~2009년생 번호의
맨 앞 `0`을 없앤 12자리 숫자 셀도 복원해 읽는다. 뒷자리 첫 숫자까지 가려졌거나 앞
6자리가 실제 날짜가 아니면 추측하지 않고 해당 행을 검토 대상으로 막는다. typed
observation과 DB에는 변환된 생년월일만 들어가며 주민등록번호 원문은 저장하지 않는다.

명단 가져오기에서 필수 인적사항은 `성명` 하나다. 생년월일·학교·주소·전화 등 선택
인적사항의 열을 연결하지 않거나 셀이 비어 있어도 신규 사람은 해당 값을 `None`으로
저장하고 가져오기를 계속할 수 있다. 식종 열 형태는 지정해야 하지만 각 사람의 식종
셀이 모두 비어 있으면 미가입으로 저장할 수 있다. 미리보기에는 연결된 항목별로
`생년월일 3명`, `학교명 2명`처럼 미입력 인원과 원본 행을 묶어 보여준다. 성명이 빈
행은 사람을 만들 수 없으므로 그 행만 제외하고, 정상 행은 계속 처리하며 제외 사유와
원본 행 번호를 revision 결정 기록에 남긴다. 반대로 값이 비어 있지 않은데 날짜 형식이
틀렸거나 식종 값이 정의되지 않았다면 임의로 고치지 않고 빨간 오류로 가져오기를 막는다.
후속 import에서 생년월일이 비어 기존 사람을 확정할 수 없으면 최종 검토에서 사용자가
신규 생성 또는 기존 사람 연결을 선택한다.

미리보기에서 셀 오류나 성명 누락 제외 행이 발견되면 화면 크기에 맞춘 별도
`명단 오류 한꺼번에 수정` 창을 연다. 메인 미리보기에는 오류 개수와 수정 창을 다시
여는 버튼만 둔다. 정정표에는 원본 행, Excel 항목명, 현재 값, 문제 설명과 `바꿀 값`
입력칸을 함께 보여준다. 사용자는 여러 오류를 한 화면에서 고친 뒤
`수정값으로 다시 검사` 한 번으로 전체 명단을 재검사하고, 오류가 모두 없어지면 수정
창은 자동으로 닫힌다. 식종 열은 조식·중식·석식 조합 또는 해당 profile의 참·거짓
값을 선택할 수 있고, 날짜·전화 등은 형식 예시를 입력칸에 표시한다. 수정값은 이번
가져오기에만 메모리에서 적용하며 원본 Excel 파일은 변경하지 않는다. 적용 중인 수정
개수와 `수정값 모두 취소`를 계속 보여주고, revision 결정 기록에는 개인정보 원문 대신
수정한 원본 행·열 위치만 남긴다. 최종 DB에는 재검사를 통과해 정규화된 값이 저장된다.

같은 성명·생년월일의 여러 행은 문자열 안의 모든 공백을 제거한 값으로 비교한다. 전화번호
칸에 대소문자와 관계없이 `str`이 들어 있으면 임시 문자열로 보고 빈값으로 처리한다. 학교
유형·학교명·학년이 행마다 다르면 교육 단계가 높은 행을 우선하고, 같은 단계에서는 학년이
높은 행을 선택한다. 학교 세 필드는 서로 다른 행에서 조합하지 않고 선택된 한 행의 값으로
함께 갱신한다. 비고는 다른 내용을 원본 행 순서대로 ` / `로 이어 하나도 버리지 않는다.
도로명주소와 상세주소는 공백을 제거한 뒤 한 값이 다른 값 전체를 포함하면 같은 주소로 보고
더 긴 값을 사용한다. 예를 들어 `수정로 1`과 `수정구 수정로 1`에서는 뒤의 값을 쓴다.
단, `수정로 1`과 `수정로 11`처럼 숫자 중간에서만 우연히 포함되는 값은 같다고 보지 않으며,
서로 포함되지 않는 주소는 이사 전·후 원본 행일 수 있으므로 아래쪽 Excel 행의 값을 현재
주소로 사용한다.

배송 담당·순서는 사람 전체가 아니라 식종별 값이다. 식종별로 나뉜 원본 행은 조식·중식·
석식의 서로 다른 담당과 순서를 그대로 보존한다. 한 원본 행에 여러 식종과 담당·순서 한
쌍만 있으면 그 값은 선택된 식종의 공통 배정으로 읽는다. 같은 식종의 여러 행에서 담당이나
순서가 다르면 아래쪽 Excel 행의 비어 있지 않은 값을 현재값으로 사용한다. 아래 행의 빈칸은
위 행의 비어 있지 않은 값을 일부러 지우는 뜻으로 해석하지 않는다.

주소·식종별 배송 담당·순서를 아래 행 우선으로 정리한 경우 원본 행 번호, 선택하지 않은 값,
현재값과 선택 기준을 import batch와 revision 결정의 `imported_delivery_history`에 함께
저장한다. 신규 DB의 첫 가져오기에도 위 행은 `가져온 이전 배송정보`, 아래 행은 현재
배송정보로 남긴다. 원본 Excel에 실제 이사일이 없으므로 이전 정보의 적용일은 임의로 만들지
않고 `unknown_from_source`로 기록한다. 더 긴 주소를 택한 경우에는 같은 주소의 덜 완전한
표기로 기록하고 이사 이력으로 단정하지 않는다. 기존 DB에 후속 명단을 가져와 실제 값이
바뀌면 통상 revision의 entity 변경 전·후도 별도로 남는다. 미리보기에는 어떤 사람의 몇 행을
현재값으로 골랐는지와 적용일 미상 기록임을 사용자가 확인할 수 있게 표시한다.

가져오기 GUI는 식종의 두 원본 모양을 실제 셀 예시로 설명하고 헤더 이름으로 자동
판별한다. 조식·중식·석식 열을 찾았으면 `조식 S열 / 중식 V열 / 석식 T열`처럼 요약만
보여주며 식종 형태와 개별 열 dropdown은 접는다. 자동 인식이 틀렸을 때만 `열 연결
바꾸기`로 펼치고, 찾지 못했으면 처음부터 입력칸을 보여준다. `flag`, `합쳐진 열과 flag
열 중 정확히 하나` 같은 내부 표현은 사용자에게 노출하지 않는다. 선택된 가구 기준은
파란 바탕의 굵은 흰색 체크로 표시한다. 닫힌 dropdown은 마우스 휠을 무시한다.
충돌 설명에는 `school_type` 같은 내부 필드명이 아니라 `학교 유형`, `도로명주소`,
`조식 배송 담당` 같은 사용자용 이름만 표시한다. 오류 정정표의 `현재 값`과 `바꿀 값`
열은 실제 내용과 선택지 길이에 맞춰 자동으로 넓어지며, 사용자가 머리글 경계를 끌어 다시
조절할 수도 있다.

암호 Excel 검사와 선택 위치/최종 명단 미리보기 생성은 UI thread 밖에서 실행하고,
진행 중에는 단계별 로딩 안내와 진행 막대를 표시한다. 암호 필요 안내 뒤 비밀번호를
입력하면 Enter 또는 다른 곳으로 focus를 옮기는 즉시 같은 파일을 다시 읽으며 별도
`다시 불러오기`를 요구하지 않는다. read-only Excel의 선행 빈 셀은 `row` 속성이 없는
`EmptyCell`일 수 있으므로 원본 행 번호는 셀 객체가 아니라 반복 위치로 계산한다.
비밀번호 입력 중 Enter는 이미 선택한 파일의 재검사에서 소비하므로 `파일 선택` 버튼으로
전달되어 Windows 파일 탐색기를 다시 열지 않는다.

`반`은 신규 Excel 열 연결, 명단 표와 사람 정보 수정 UI에서 사용하지 않는다. 기존 DB의
`class_name` 필드는 이전 데이터 호환을 위해 유지하며, 다른 정보를 수정하거나 후속 import를
해도 화면에 드러나지 않은 기존 값은 지우지 않는다.

DB 명단 표의 표시 열은 머리글을 누르면 정렬된다. 빈 셀도 정렬 결과의 한쪽에 모이므로
별도의 미입력 전용 테이블이나 중복 저장소는 만들지 않는다. 미입력 여부는 언제나 현재
DB snapshot의 실제 값에서 확인한다.

일반·방학 중식 reconciliation은 정규화한 성명＋핸드폰이 기존 사람 한 명과
일치하고 원본에 같은 성명＋핸드폰 중복이 없으면 자동 연결을 우선한다.
핸드폰의 하이픈·공백은 무시하며 빈 번호는 일치로 보지 않는다.
자동 연결되지 않은 행은 성명＋세대주명이 같으면 핸드폰이 다르거나 없어도
동일인 의심으로 검토한다. 성명·세대주명은 공백을 무시하고 빈 세대주명끼리는
일치로 보지 않는다. 원본의 성명＋세대주명 중복도 검토하며 기존의 동명이인·
원본/DB 중복 검토와 일반 명단의 성명＋전체 생년월일 보조 판정은 유지한다.
`확인 행 모두 신규 등록`은 검토 행마다 새 사람 ID를 생성하고 자동 연결된 행은
유지한다. 가구 묶기와 중식 누락자 중지는 각각 기존 규칙을 따른다.
확정된 식종 변경은 import 적용일을 기준으로 가입 기간을 닫거나 새 기간을 연다.

후속 import의 인적사항 update policy version 1은 **매핑된 빈 셀로 기존 값을
지우지 않는다**. 기존 사람에게 연결된 observation의 빈 학교·주소·전화 등은 현재
DB 값을 유지하고 변경 목록에도 삭제로 표시하지 않는다. 값이 들어 있는 매핑 셀만
기존 값을 갱신한다. 신규 사람은 보존할 기준 profile이 없으므로 빈 셀을 `None`으로
저장한다. 이 정책은 인적사항에만 적용하며, 개별 식종 여부 열의 빈칸은 import profile에
정의된 `급식을 받지 않는 값` 의미를 그대로 따른다. 정책 version과 observation별로 실제 유지한
필드 목록은 revision 및 import batch 결정 manifest에 남긴다.

기존 인적사항을 일부러 지울 때는 Excel 빈칸이나 특수문자를 사용하지 않는다. 명단에서
사람을 선택한 뒤 `정보 수정` 화면에서 해당 칸을 직접 비우며, 화면은 저장 전에
`삭제 예정` 필드를 보여주고 한 번 더 확인한다. 성명은 필수이고 생년월일 형식을
검사한다. 승인된 변경은 `person_profile_edit_policy_version=1`인 UI revision으로
저장하며 변경 필드와 삭제 필드를 결정 manifest에 남긴다. 이 수정은 가구 membership,
식종 가입, 배송 배정과 사용자 정의 값을 건드리지 않는다.

## Import 가구 묶기

가구 묶기와 사람 identity reconciliation은 서로 다른 결정이다. 가구가 같아도
사람 레코드는 각각 유지하며, `이 사람만 별도 가구`는 그 사람의 household
membership만 별도 ID로 바꾼다.

- GUI에서 핸드폰, 세대주 성명, 주소, 전화번호 중 하나 이상을 선택한다. 기본은
  핸드폰 하나다.
- 선택한 모든 기준이 비어 있지 않고 모두 일치할 때만 같은 가구로 제안하는 AND
  규칙이다. 하나라도 비어 있으면 다른 값이 같아도 묶지 않는다.
- 핸드폰·전화번호는 숫자로 정규화하고, 세대주 성명과 주소는 Unicode를 정규화한 뒤
  모든 공백을 제거해 비교한다. 주소는 비어 있지 않은 도로명주소와 상세주소 조합을
  비교한다.
- 제안되지 않은 신규 사람은 처음부터 각자 다른 household ID를 받는다.
- 후속 import는 적용일에 유효한 기존 household membership의 구성원도 같은 AND
  rule로 비교한다. 선택 기준 전체가 한 기존 구성원에게서 함께 일치해야 한다.
- 기존 가구가 하나만 일치하면 기본 후보로 제안하고, 둘 이상이면 자동 선택하지
  않는다. 최종 검토에서 구성원 이름과 일치 근거를 보고 기존 가구 하나 또는 별도
  가구를 반드시 선택한다.
- 최종 검토에서는 plan이 허용한 기존 household ID, 신규 shared ID 또는 사람별
  separate ID만 선택할 수 있다.
- membership은 import 적용일부터 열린 기간으로 기록한다. 선택 기준, AND 방식,
  빈칸 제외와 정규화 version은 `household_matching_rule` 이력에 남긴다.

기존 사람으로 identity 연결된 행은 원래 household membership을 유지한다. 신규
사람에게만 확정한 기존 또는 신규 household membership을 적용한다.

## 여러 식종 배송 상태 변경

명단의 기존 우클릭 동작인 `배송`, `일시중지`, `중지`는 선택한 한 식종만 바로
저장하지 않고 최종 변경 화면을 연다. 이 화면에서 조식·중식·석식을 하나 이상
선택하고, 선택한 모든 식종에 같은 상태와 같은 inclusive 기간을 적용한다. 서로 다른
상태나 기간이 필요하면 별도 변경으로 저장한다.

- 모든 상태에는 시작일이 필요하며 기본값은 명단에서 보고 있던 서비스일이다.
- `일시중지`는 시작일과 종료일이 모두 필요하다.
- `배송`과 `중지`는 종료일을 비워 `계속`으로 둘 수 있다.
- 시작일에 가입된 식종만 `일시중지`나 `중지`할 수 있다.
- 미가입 식종에 `배송`을 지정하면 요청한 배송 기간을 덮도록 meal enrollment를
  자동 추가한다. 유한한 배송이면 가입도 그 기간까지만이며, 기존 가입 기간과
  겹치거나 맞닿으면 하나의 연속 기간으로 합친다.
- `중지`는 가입 이력을 삭제하지 않는다. 나중에 `배송` 사건을 기록하면 중지와 재개
  원문은 모두 남고 유효 상태만 날짜별로 다시 계산한다.

선택한 식종마다 append-only `StatusEvent`를 하나씩 만들되 모두 같은 UI revision에
저장한다. 결정 manifest에는 사람, 식종 목록, 상태, 기간과 자동 가입된 식종을 남긴다.
화면은 저장 전에 식종별 `현재 → 변경 후`를 보여준다.

## 식종별 청구 단가

SQLite v2의 기본 단가는 조식·중식·석식 모두 **10,000원**이다. 기존 Excel 앱의
전역 설정 기본값 9,500원은 legacy 회귀 기준일 뿐 새 DB의 기본 단가로 이어받지 않는다.

명단 화면의 `단가 관리`에서 다음 순서로 변경한다.

```text
식종 한 개 이상 선택 → 새 단가 입력 → 적용일 선택 → 변경 결과 확인 → 저장
```

- 여러 식종을 선택하면 같은 단가와 같은 적용일을 한 번에 적용한다.
- 식종마다 다른 금액이면 변경을 나누어 저장한다.
- 적용일 당일부터 새 단가가 유효하다.
- 기존 변경을 고치거나 삭제하지 않고 raw 단가 변경으로 추가한다.
- 같은 식종·적용일을 다시 저장하면 나중에 기록한 변경이 우선한다.
- 과거 적용일을 나중에 추가해도, 그보다 뒤 적용일에 이미 정한 단가까지 덮지 않는다.
- 저장은 일반 UI revision으로 변경번호를 만들고 자동 DB 백업을 실행한다.

문서를 만들 때는 선택한 source revision 안의 단가 schedule만 사용하고 실제 적용한
식종별 단가를 document run의 계산 manifest에도 남긴다. 따라서 이후 단가 변경은
이미 만든 문서의 금액이나 재생성 결과를 바꾸지 않는다.

월 중간에 단가가 바뀌면 **서비스일별로 나눠 계산**한다. 식종별 총 식수는 그대로
합치되 금액은 그날 유효한 단가별 식수와 소계를 더한다. 예를 들어 중식이 9월
15일부터 10,000원에서 11,000원으로 바뀌고 변경 전 10식, 변경 후 12식이면 총 식수는
22식이고 금액은 `10식×10,000원 + 12식×11,000원 = 232,000원`이다.

`price_entitlements`는 같은 사람·식종·서비스일 entitlement의 중복 청구를 거부하고,
사람·식종·단가별 서비스일을 근거로 보존한다. document calculation manifest에는
청구 시작일·종료일, pricing mode, policy version, 사람별 식종·단가·식수·소계와 총액을
남긴다. manifest를 만들 때 실제 계산에 사용한 schedule과 다른 단가표를 넘기거나 청구
기간 밖의 서비스일이 섞이면 실패한다.

기존 청구서 본문은 식종별 총 식수와 청구 총액을 계속 사용한다. 청구월 안에서 한
식종의 유효 단가가 실제로 두 구간 이상이면 문서 전체에 한 번 쓰는 `전체 비고`를
자동으로 만든다. 같은 적용일·구간의 여러 식종은 하나로 묶어 표시하며 계산 manifest에도
그 문구를 남긴다. 새 단가가 청구월 1일부터 적용되어 그달 전체 단가가 하나뿐이거나,
월중에 같은 금액을 다시 저장해 실질적인 단가 구간이 갈리지 않으면 비고를 만들지 않는다.
사람별 원본 `비고`는 이 문구로 덮거나 합치지 않는다. 기존 Excel 템플릿에 전체 비고를
위한 별도 행을 추가하지 않고, 각 출력 시트의 데이터 시작 직전 **소계 3행에 이미 있는
`비고` 셀**에 표시한다. 청구서에 연월이 이미 있으므로 문구는
`중식 단가: 1~14일 10,000원 / 15~30일 11,000원`처럼 날짜의 일만 쓰고 별도 계산
설명은 붙이지 않는다. 혼합 단가가 없으면 그 셀은 기존처럼 비워 둔다.

## 업체 휴무와 대체식

운영 DB 하나가 업체 하나의 일정을 대표하므로 화면에서 업체를 다시 고르지 않는다.
명단 상단 `휴무·공휴일`을 열면 앱에 포함된 한국 공휴일 달력이 연도별 **검토 후보**를
만든다. 후보를 목록에 표시하는 것만으로 DB, 배송 또는 청구는 바뀌지 않는다. 날짜는
기본으로 아무것도 선택하지 않으며 사용자가 체크한 한 개 이상의 공휴일에 같은 식종과
처리 방법을 일괄 적용한다. `미검토 전체 선택`은 검토가 덜 끝난 날짜만 체크한다. 기본
전체인 조식·중식·석식 중 적용 식종을 고른 뒤 `정상 운영`, `미제공`, `대체식 제공` 중
하나를 명시적으로 저장해야 반영한다. 일부 식종만 저장하면 나머지는 계속 `미검토`로
표시한다. 이미 검토한 날짜·식종을 다시 선택하면 저장 전에 재기록 범위를 경고하며 이전
이력은 지우지 않는다.

공휴일 후보에는 날짜·한국어 이름·달력 제공자와 version을 함께 고정해 어느 기준을 보고
확정했는지 남긴다. 달력은 실행 중 인터넷을 조회하지 않는다. 앱에 포함된 달력 version에
아직 없는 임시공휴일은 새 앱 version을 받기 전까지 자동 후보로 나타나지 않을 수 있으므로
그 사이에는 `공휴일 아닌 휴무 직접 추가`로 등록할 수 있다.

업체 자체 휴무는 날짜가 공휴일인지와 관계없이 시작일과 종료일을 inclusive 기간으로
등록할 수 있다. 조식·중식·석식을 기본으로 모두 선택하되 필요하면 일부 식종에만 적용한다.
같은 날짜·식종에 나중 변경을 저장하면 원본 변경은 지우지 않고 나중 변경이 계산상
우선한다.

공휴일 후보의 `정상 운영`은 평소 배송과 청구를 유지했다는 검토 결과를 기록한다. 실제
휴무로 정한 선택 식종은 다음 두 방식 중 하나로 처리한다.

- `미제공 · 청구 제외`: 실제 배송이 없고 원래 식사일 entitlement도 만들지 않는다.
- `대체식 제공 · 청구 포함`: entitlement와 청구는 원래 식사일에 유지하고 실제 제공일만
  별도로 저장한다.

업체 자체 휴무의 대체식 기본 실제 제공일은 선택 기간 전체에 공통으로 적용하며 직전
운영일을 제안한다. 사용자가 `날짜별로 다르게 지정`을 켜면 원래 식사일×식종별 실제
제공일을 바꿀 수 있다. 공휴일 여러 날을 일괄 검토할 때는 처음부터 선택한
공휴일×식종별 실제 제공일 표를 보여준다. 표의 기본값은 주말과 해당 연도의 공휴일
후보를 건너뛴 직전 운영일이며 실제 제공일이 다른 칸만 바꾼다. 예를 들어 9월 10일 중식
휴무분을 9월 9일 대체식으로 제공하면 배송표에는 9일, 청구에는 원래 식사일인 10일의
1식으로 반영한다. 선택한 공휴일 N일은 날짜별 변경 항목으로 남지만 schedule AuditChange,
변경번호와 자동 백업은 각각 하나로 원자 저장한다.

## 문서 만들기 진입점

명단 상단에는 청구서·확인서·일일식수·배송대타 버튼을 각각 늘어놓지 않고
`문서 만들기` 버튼 하나만 둔다. 선택 화면은 사용자가 업무 이름으로 찾을 수 있도록
`정산 문서`의 청구서·확인서와 `배송 문서`의 일일식수·배송대타로 구분한다. 문서 종류를
한 번 누르면 선택이 확정되고, 다음 화면에서 문서에 사용할 변경번호를 고른다.

변경번호는 현재 최신 revision이 기본이다. 사용자가 `이전 변경번호로 만들기`를 직접 열어
과거 행을 고른 경우에만 예전 snapshot을 사용한다. 앱은 선택한 문서 종류와 정확한
`RevisionSummary`, 명단 화면에서 보고 있던 날짜를 하나의 문서 설정 요청으로 넘긴다.

기간 기본값은 실제 오늘이 아니라 **명단 화면에서 보고 있던 날짜**를 기준으로 한다.
청구서·확인서는 그 날짜가 속한 달의 1일부터 실제 말일까지를 제안하며 사용자는 다른
연·월로 바꿀 수 있다. 일일식수는 그 날짜 하루를 제안하되 시작일·종료일 범위로 넓힐
수 있다. 배송대타는 기존 업무와 같이 하루 날짜만 선택한다. 확정한 `DocumentPeriodSelection`은
문서 종류, source 변경번호, 화면 기준일과 실제 시작일·종료일을 함께 가진다. 아직 파일을
만들기 전이므로 종류·source·기간 선택 자체는 DB revision이나 자동 백업을 만들지 않는다.

기간 다음에는 문서에 넣을 식종을 확인한다. 청구서·확인서·일일식수는 누락을 막기 위해
조식·중식·석식을 기본으로 모두 선택하며, 사용자가 필요 없는 식종을 해제할 수 있다. 단,
최소 한 식종은 남아야 한다. 배송대타는 담당자 한 명의 한 식종 배송표이므로 식종 하나만
선택하고, 명단 화면에서 보고 있던 식종을 기본으로 보여준다. 이 화면의 선택도 문서 생성
입력일 뿐 명단 DB를 수정하거나 revision·자동 백업을 만들지 않는다. 확정한
`DocumentMealSelection`은 앞 단계의 문서 종류·source·기간과 최종 식종 목록을 함께 가진다.

식종 확인 다음에는 저장 폴더를 확인한다. 이 컴퓨터의 기본 문서 폴더는 QSettings에 경로만
기억하고 운영 DB, revision, document run 또는 자동 `.mealbackup`에는 전체 경로를 넣지
않는다. 기본 폴더가 있으면 그대로 제안하고, 사용자는 `이번만 다른 폴더`를 골라 해당 문서에만
다른 위치를 사용할 수 있다. 이번만 선택은 기억한 기본 폴더를 바꾸지 않는다. `기본 폴더 변경`을
확정한 경우에만 이후 문서의 기본값을 새 폴더로 바꾼다. 기본 폴더가 아직 없거나 이동·분리되어
찾을 수 없으면 임의의 다른 위치에 저장하지 않고, 존재하는 새 기본 폴더를 고를 때까지 생성을
막는다. 확정한 `DocumentOutputSelection`은 앞 단계의 모든 입력과 존재하는 출력 폴더, 기본/
새 기본/이번만 사용 방식을 함께 가진다.

파일명은 사용자가 입력하지 않는다. 기간, 문서 종류, 일부 식종 또는 배송대타의 식종,
source 변경번호를 조합해 자동 생성한다. 조식·중식·석식 전체이면 식종 표기는 생략한다.
예시는 `2026-08_청구서_20260831-005.xlsx`,
`2026-08-17_배송대타_중식_20260831-005.xlsx`다. 같은 이름이 이미 있으면 기존 파일을
덮어쓰지 않고 `_재발행02`, `_재발행03`을 순서대로 붙여 처음 비어 있는 이름을 사용한다.
생성 직전에도 같은 함수를 다시 적용해 출력 경로가 여전히 비어 있는지 확인해야 한다.
`DocumentOutputSelection`은 최종 파일명과 재발행 번호를 함께 가지며 document run에는
기존 계약대로 전체 폴더 경로 없이 파일명만 저장한다.

저장 위치를 골랐다는 사실만으로는 생성 완료로 처리하지 않는다. 최종 파일이 실제로
존재하고 비어 있지 않으며, 생성 결과에 기록한 파일 크기와 SHA-256이 현재 파일 bytes와
일치할 때만 `GeneratedDocumentResult`를 만든다. 완료 화면을 열 때와 `파일 열기`를 누를
때도 같은 검증을 다시 수행한다. 파일이 사라졌거나 생성 뒤 내용이 바뀌었으면 성공 화면이나
파일 열기를 진행하지 않고 오류를 보여준다.

정상 생성 뒤에는 Excel이나 탐색기를 자동으로 열지 않는다. 완료 화면에 정확한 파일명,
문서 종류·기간·식종·원본 변경번호, 생성 시각, 파일 크기와 저장 폴더를 보여주고 사용자가
`파일 열기`, `폴더 열기`, `닫기` 중 직접 고르게 한다. 파일이나 폴더 열기 요청이 실패해도
완료 화면은 닫지 않고 같은 화면 안에 원인과 다음 행동을 표시한다.

명단 화면의 `설정` 버튼은 `생성 Excel 비밀번호`, `청구서·확인서 양식`,
`문서 저장 폴더`를 분리해 보여준다. 양식은 이 업체 DB에 `급식` 또는 `행복도시락` 중
하나로 저장하고 이후 자동 사용한다. 비밀번호·양식 변경은 DB revision과
자동 백업을 만들지만, 컴퓨터 로컬 폴더 변경은 명단 업무 데이터가 아니므로 변경번호와
자동 백업을 만들지 않는다.

청구서나 확인서를 처음 만들 때 양식 또는 비밀번호가 아직 없으면 문서 종류를 고른 직후
한 번만 설정 화면을 연다. 설정 revision을 저장한 뒤 변경번호 목록을 새로 읽으므로 새
설정까지 포함된 최신 상태를 원본으로 고를 수 있다. 계산용 명단·가입·상태·학교 일정·휴무·
단가는 사용자가 고른 source revision에서만 읽고, 파일 보호 비밀번호와 내장 양식 선택은
생성 시점의 현재 DB 설정을 쓴다.

청구서와 확인서는 같은 entitlement 계산 결과로 실제 암호화 Excel을 만든다. 청구서는 월중
단가 변경까지 계산한 정확한 숫자 금액을 쓰고, 확인서는 DB의 안정적 household ID로 가구를
묶어 같은 주소의 서로 다른 가구를 합치지 않는다. 가구 묶음은 선택한 원본 변경번호의
문서 종료일(월간 문서는 해당 월 말일) 소속을 사용한다. 기준일에 소속이 없으면 문서에 포함된
식사일 중 소속이 확인되는 가장 늦은 날짜의 가구를 사용한다. 기준일과 포함된 식사일 모두에
유효한 소속이 없을 때만 대상자·기준일·기록된 기간을 안내하고 생성을 중단한다. 월중에 다른
가구로 옮겼거나 잠시 옮겼다가 돌아왔다는 이유로 월간 문서를 막지 않는다.
가구 묶음은 출력 배치에만 적용하며 식수·주차별 수량·단가는 기존 날짜별 계산을 유지한다.
원본 가구 소속 이력은 수정하지 않고 일일식수·배송목록의 날짜별 가구 검증도 유지한다.
계산 manifest의 월간 문서 계약 버전은 6, document_presentation 정책 버전은 2이며
가구 기준(document_period_end)과 대체 규칙(latest_service_day_with_membership)을 기록한다.
생성 직전에 파일명을 다시 확인해 기존
파일을 덮어쓰지 않으며, 파일 생성과 append-only document run 저장이 모두 성공해야 완료로
표시한다. run 저장이 실패하면 방금 만든 파일을 되돌리고, 성공한 run 뒤에는 자동 백업을
만든다.

확인서 주차는 월요일부터 일요일까지 나누고 기본으로 해당 월의 날짜만 표시한다.
문서 양식의 다음 달 주말 표시 옵션을 켜면, 월말이 금요일·토요일인 경우 마지막 주의
표시 종료일만 다음 달 일요일(1일 또는 2일)로 늘린다. 이 옵션은 식수·금액·계산 주차를 바꾸지 않으며,
식수는 기존 다음 달 식수 포함 설정을 따른다. 연말에도 적용하고 생성 기록에 옵션을 남긴다.
예를 들어 2026년 10월 첫 주는 10월 1~4일로, 금·토·일 조식이 같은 주에 들어간다.
6주가 되는 달은 확인서의 5주 칸에 맞춰 토요일 시작이면 마지막 두 주를,
일요일 시작이면 처음 두 주를 합친다. 식수의 배송일·서비스일 기준과 월 합계는 유지한다.

행복도시락 방학 청구서의 `학기중` 시트는 조식·석식, `방중` 시트는 중식의 식수와
청구금액만 합산한다. 혼합 식종 대상자는 두 시트에 각각 해당 식종의 내역으로 표시하고,
두 시트의 합계는 `총괄`과 일치해야 한다. 금액은 서비스일별 단가를 반영한 식종별 금액을
사용하며 전체 금액을 식수 비율로 나누거나 월초 단가로 다시 계산하지 않는다. 식수 칼럼에
다른 명단 항목을 연결해도 시트의 계산 범위는 유지한다. 일반 월의 학기중·총괄은 기존처럼
포함된 전체 식종을 표시한다.

일일식수는 공통 비밀번호 설정 여부와 관계없이 비밀번호 없는 Excel을 만든다.
비밀번호 설정 화면을 열지 않고 생성 기록의 `export_password.protected`는 `false`로 남긴다.
선택 기간은 서비스일이
아니라 **실제 배송일 범위**다. 선택한 historical snapshot의 가입·상태·학교 일정·휴무·
대체식·개인별 제공 요일·배송요일을 함께 계산하므로 금요일의 주말분 묶음과 휴무 때 따로 저장한 대체식은
실제 제공일 시트에 잡힌다. 담당자별로 안정적 household ID를 묶어 1~5인 가구 수와 총 인원을
계산하고, 같은 식종의 같은 연도 직전 실제 배송일과 달라진 칸을 기존 양식 방식으로 표시한다.
별도 배송 형태가 있으면 담당자 행의 기존 `비고` 칸에 기본 및 각 형태별 실제 배송
가구 수와 식수를 표시한다. 예를 들어 `기본 1가구·2식`, `식재료 박스 1가구·2식`으로
구분하되, 가구원 수별 합계와 총 인원은 모든 형태를 합친 물리 배송 현황을 유지한다.
같은 비고 칸에는 식종별 시작·중지·일시중지와 복원 안내를 담당자·상태·관할동별로 묶어
표시한다. `신규`는 식종 가입 시작일을 기준으로 하며 행 삽입일이나 DB 등록일을 사용하지
않는다. 상태는 선택한 변경번호의 유효한 상태 기간을 따르고, 배송이 없는 중지·일시중지
대상자도 비고에는 포함한다. 원본 일일식수매크로처럼 이번 주 월요일 전 22일 이내의 마지막
평일 배송일과 이번 주 조회일까지의 배송일을 참고한다. 조식은 이전 배송일과 조회일만
참고하며, 일시중지 안내 뒤 기간이 끝나면 `복원`을 표시한다. 이름은 관할동별로 묶고
위례동은 주소의 동·호수 등을 사용한다. 비고 대상자를 추가해도 배송 가구 수와 식수는 늘리지 않는다.
배송담당이 비어 있거나 한 실제 배송에 서로 다른 가구 소속이 섞이거나 6인 이상 가구가 있으면
현재 양식으로 조용히 잘라 쓰지 않고 생성을 막아 원인을 알린다.

리포트의 source 변경번호, 실제 배송일 범위, 식종, 조식 policy manifest, 학교 일정·휴무
근거, 가구 집계 rule, 템플릿·평문/암호문 hash를 `delivery_report` document run에 남긴다.
파일 생성 뒤 run 저장이 실패하면 방금 만든 파일을 되돌리고, 성공하면 자동 백업한다.
배송대타 writer 연결은 아직 별도 후속 범위다.

## 생성 Excel 공통 비밀번호

명단 화면의 `설정`에서 센터 공통 Excel 비밀번호를 한 번 저장한다. 이후 SQLite v2가
만드는 청구서·확인서·명단 및 일일식수를 제외한 개인정보가 포함된 Excel에는 같은 비밀번호를 자동으로
적용하며 생성할 때마다 다시 묻지 않는다. 비밀번호가 아직 설정되지 않았으면 보호되지
않은 파일을 대신 만들지 않고 설정 화면으로 안내한다. 일일식수만 비밀번호 없이 생성하며
저장된 공통 비밀번호와 다른 문서의 보호 설정은 변경하지 않는다.

설정 화면에는 암호화 DB의 **현재 비밀번호 한 개만** 처음에는 가린 상태로 표시한다.
`현재 비밀번호 보기`를 누르면 30초 뒤 자동으로 다시 가리고, `복사`로 클립보드에 넣은
값도 30초 뒤 지운다. 그 사이 사용자가 다른 내용을 복사했다면 새 클립보드 내용은
건드리지 않는다. 이미 운영 DB를 열어 사용 중인 화면이므로 확인할 때 비밀번호를 다시
묻지는 않는다. 과거 버전의 비밀번호는 일반 설정 화면에서 목록으로 보여주지 않는다.

비밀번호 원문은 QSettings, document run, 계산·템플릿 manifest, 로그에 넣지 않고
암호화 DB의 `export_password_setting` revision entity에만 저장한다. 화면과 공개
manifest에는 설정 여부, policy version, 설정 version과 비밀번호를 바꾼 revision ID만
남긴다. 설정을 바꾸면 변경번호와 자동 백업이 만들어지고 이후 생성 파일부터 새
비밀번호를 쓴다. 예전 비밀번호는 예전 파일 재현을 위해 암호화된 과거 revision 안에서만
유지하며 일반 화면에서는 조회하지 않는다.

비밀번호를 적용하는 Excel의 암호화는 Microsoft Office 자동화에 의존하지 않는다. workbook 평문은 메모리에만
만들고 대상 폴더에는 암호화된 staging 파일만 쓴 뒤, 암호 적용 검증이 끝나야 최종 파일로
원자적으로 교체한다. 실패하면 같은 이름의 기존 파일은 그대로 둔다.

## 과거 변경과 청구서·확인서

과거 날짜로 상태를 변경해도 예전에 만든 청구서·확인서의 의미를 바꾸지 않는다.
각 문서는 생성 당시 선택한 revision snapshot의 결과로 남고, 나중 revision 때문에
기존 문서에 경고나 `재생성 필요` 표시는 붙이지 않는다. 수정 내용을 반영해야 할 때는
새 revision으로 새 문서를 만들며 예전 문서 run과 파일을 덮어쓰지 않는다.

예를 들어 8월 청구서를 변경번호 `20260820-004` 기준으로 만든 뒤 8월 17일의 중지
기록을 `20260826-003`에서 추가했다면, 기존 청구서는 계속 `20260820-004` 결과다.
정정 청구서가 필요할 때만 `20260826-003`을 source로 새 문서 run을 생성한다. 두
문서의 계산 rule과 template version도 각 run에 따로 남겨 같은 결과를 재현한다.

새 문서의 source는 현재 최신 변경번호가 기본이다. 이 기본 선택은 별도 목록을 먼저
보여주지 않으며, 사용자가 `이전 변경번호로 만들기`를 눌러 과거 행을 직접 골랐을
때만 바뀐다. 과거 source에는 그 뒤에 저장한 수정이 포함되지 않는다고 표시한다.
문서 생성 이력은 roster revision과 별도이므로 같은 명단으로 청구서와 확인서를 여러
번 만들어도 명단 변경번호는 증가하지 않는다.

자동 `.mealbackup`은 생성된 Excel 파일 자체를 보관하지 않는다. 파일을 잃으면
document run에 기록된 원본 변경번호, 계산 version, template version으로 자동 생성
결과를 다시 만든다. 비밀번호 암호화는 같은 내용도 매번 다른 bytes를 만들 수 있으므로
`output_sha256`은 당시 발행 파일 자체를 식별하고, template manifest의 평문
`content_sha256`은 재생성한 workbook 내용이 같은지 확인하는 데 사용한다.
사용자가 생성된 Excel을 직접 고친 내용은 DB 이력이 아니므로 다시 만들어지지 않으며,
DB와 자동 백업을 모두 잃은 상태에서 청구서 파일만으로 운영 DB를 복구할 수도 없다.


## 출력 칼럼 연결 수정

`설정 → 출력 칼럼 연결`에서 가져오기가 끝난 명단의 항목과 출력 양식의 칼럼을
다시 연결한다. 급식·행복도시락 및 청구서·확인서의 연결은 구분해서 저장한다.
식수·청구금액·연번은 자동 산출 규칙을 유지한다. 기본 연결로 초기화할 수 있고,
취소하거나 같은 연결을 저장하면 새 revision을 만들지 않는다.

이 연결은 원본 Excel 열을 명단 항목으로 변환하는 가져오기 매핑과 별개다.
연결을 저장해도 현재 명단 값과 이미 생성한 파일을 수정하지 않으며, 이후 문서 생성은
현재 저장된 연결을 사용한다. 과거 명단 revision을 원본으로 선택해도 출력 연결은
현재 설정을 사용하며 실제 사용한 연결은 document run에 함께 기록한다.

## 직접 추가한 명단 행의 가구 소속

명단 행 추가에서 기존 가구가 확정되면 해당 가구에 소속시키며, 일치하는 가구가 없으면 별도 가구를 만든다. 새 행의 최초 가구 소속은 시작일 제한 없이 저장하고 실제 배송 자격은 식종 가입 시작일로 제한한다. 연락처만으로 나중에 다른 가구에 합치지 않는다.

방학 중식 가져오기에서도 새 대상자는 가져오기 적용일부터 각각 별도 가구에 소속시킨다.

과거 명단 행 추가와 방학 중식 가져오기 기록의 소속 누락은 `설정 → 가구 소속 기록 복구`에서 명시적으로 검토한다. 최초 추가 이력에 소속이 없고 그 뒤 소속 이력이 전혀 없는 현재 대상자만 별도 가구로 복구한다. 적용 시작일은 저장된 식종 가입 기간의 가장 이른 시작일이다. 가입 기간이 없거나 이후 소속을 추가·삭제한 경우는 자동으로 추정하지 않는다. 복구는 새 변경번호로 저장하며 과거 변경번호를 변경하지 않는다.


최초 행 추가 이력의 소속 하나가 종료 없이 그대로 남았고 이후 소속 변경 이력이 없다면, `설정 → 가구 소속 기록 복구`에서 소속 시작일을 저장된 가장 이른 식종 가입일로 앞당길 수 있다. 대상과 기존·변경 날짜를 미리보기로 확인한 뒤 새 변경번호로 저장한다. 이후 가구 이동·종료·공백이나 소속 정정 이력이 있는 대상은 제외하며 기존 가구 ID·가입·상태·과거 변경번호는 유지한다.


## 운영 DB 가구 묶기 기준 (2026-10-29)

- 가구 기준은 운영 DB에 선택한 기본·사용자 칼럼으로 저장한다. 설정이 없으면 핸드폰을 사용하며, 여러 칼럼은 모두 일치해야 한다. 빈 값은 일치로 보지 않고 전화 계열 기본 칼럼은 숫자로 비교한다.
- 설정 적용 시 현재 명단도 합치고 이후 명단 불러오기·행 추가·선택 칼럼 수정에 같은 기준을 적용한다. 이전 소속·예약 소속은 보존하고 기존 가구를 자동 분리하지 않는다. 공용 설정과 묶기 기준은 서로 독립적이다.
